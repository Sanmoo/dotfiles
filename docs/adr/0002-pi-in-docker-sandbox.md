# Pi runs in a plain Docker sandbox with the declared environment installed inside it

Pi had the run of the home directory: every command the agent ran could read or modify other repositories, the dotfiles checkout, and the credentials in the Pi agent directory. The decision is to run Pi through a `safe-pi` wrapper in a throwaway Docker container that mounts the working repository read-write at its host path, mounts the Pi agent directory, the configuration checkout, the shared skills directory, the Herdr socket directory, git and SSH material (extensions and Pi packages held read-only), mounts a named volume holding a toolchain installed inside the container from the repository's tracked mise configuration, and mounts nothing else — no host toolchain, no Docker socket. Herdr state attribution comes from a sandbox-owned reporter extension that reports over the mounted socket under its own source, because Herdr ignores the Herdr-managed integration for a pane whose foreground process is `docker`; the sandbox therefore withholds the variables that activate the managed integration and loads the reporter explicitly. Herdr's automatic session resume comes from the resume command the reporter declares for itself: Herdr stores the reported `resume_argv` (`safe-pi --session <id>`) with the pane and, after a server restart, types it into the restored pane's shell in the saved working directory, so the pane comes back inside a fresh sandbox in the same conversation rather than as a plain shell or an unsandboxed Pi.

## Considered Options

- **Compile Erlang/OTP from source in the image** (adding `libncurses-dev`, `libssl-dev`, `autoconf`). Rejected: a ~1 MB package add, but a ~20-minute build, and — with OTP declared as `latest` — a fresh ~20-minute build inside a start every time OTP releases. Its failure mode is also the worst measured here: mise keeps no record of a failed install, so the 107 MB OTP source archive was re-downloaded and `configure` re-run on every start, 52–53 s each time, before the fail-open warning.
- **Use the precompiled build while keeping `latest`.** Rejected: Bob publishes an OTP release's build up to ~15 minutes after the release, so a start inside that window failed. The pin removes the window, and `erlang.compile = false` makes a missing build fail cheaply and loudly instead of falling back to the source build.
- **Retire erlang and elixir from the declaration**, leaving them to the per-repository `.mise.toml` of a project that needs them. Rejected: no repository in the home tree uses them, so this would remove them from the host's global toolkit as well and only postpone a working sandbox install that costs 11 seconds once.
- **Pin the sandbox to glibc's built-in `C.UTF-8`**, rewriting or dropping the forwarded locale. Rejected because it changes behaviour the host's locale governs: `C.UTF-8` is POSIX collation, time, and messages with a UTF-8 charmap, so `sort` order, `date` names, and message language would differ from the host while `locale charmap` looked right.
- **Silence the Erlang VM with `ELIXIR_ERL_OPTIONS="+fnu"`.** Rejected: it fixes Elixir alone, leaves the rest of the toolchain on the POSIX charmap, and asks the VM for UTF-8 filenames whatever the filesystem's locale is.
- **Let the wrapper forward only a locale the image can honour.** Rejected because the wrapper has no way to know: it would have to query the image on every start, and a direct image run would still fall back to POSIX. The container can answer that question itself, so the entrypoint does.
- **Pass the host's locale into the image build** (a `LOCALE` build argument the wrapper fills from `LANG`). Rejected: it would make the image honour exactly one locale by construction, but the value lands in the layer chain before mise and Pi are installed, so a host locale change would rebuild the image's expensive layers, while the entrypoint's availability check costs nothing at start.
- **Mount the host toolchain** (the mise installs and `~/.local/bin`) instead of installing a toolchain inside the container. Rejected after measuring: several core host binaries fail in a Debian-based image (Node without `libatomic`, `fd`, `jq`), and making them work requires matching the host distribution, which couples the sandbox to host upgrades and blurs the very boundary the sandbox exists to draw.
- **Bake the whole toolchain into the image.** Rejected because the declaration is full of `latest` pins: they would freeze at image build, and a repository pin that differs from the declaration would re-download on every run, since a `--rm` container discards what was installed at runtime.
- **Docker Sandboxes, OpenShell, or Gondolin** instead of plain Docker. Rejected for a single-user workstation: they add proxy, policy, and (for Gondolin) VM machinery whose credential-handling benefits this setup does not need, while making the Herdr-facing behavior harder to reason about.
- **Mount the agent directory read-only**, keeping only credentials and sessions writable. Rejected because it does not work: Pi creates a lock file next to the credential file, so a read-only agent directory fails credential loading outright.
- **Full read-write parity for the agent directory**, without read-only sub-mounts. Rejected so that a bad turn cannot persist code changes (extensions, Pi packages) into the host setup.
- **Shadow `pi` on `PATH`** so Herdr's resume command re-enters the sandbox automatically. Rejected: it changes every `pi` invocation on the host (Herdr's agent start, the WorkQ launcher, one-shot print runs) and requires adopting an unmanaged wrapper file, and its failure mode is the worst one — a broken restore path. The container-side integration that reports its own resume command was spiked on Herdr 0.9.3 and adopted instead, so no host `pi` invocation changes.

## Consequences

- The SSH agent and Herdr sockets are bind-mounted by host path, which assumes the Docker daemon runs on the host itself. On macOS the daemon runs in a VM; ADR 0008 records how the sockets reach the sandbox there.
- Sandboxed panes restore through a self-reported resume command, not Herdr's native session reference, which is stored only for official `herdr:*` sources: the reporter attaches `resume_argv` (`safe-pi --session <id>`, naming the session that was running), and Herdr types it into the restored pane's shell in the saved working directory. The pane comes back as a fresh sandbox in the same conversation, never an unsandboxed Pi and never another session in the same directory. A pane whose reporter never reached Herdr has no stored command and falls back to a plain shell, which `safe-pi -c` recovers.
- The command was verified against Herdr 0.9.3 before release. A fresh pane in an isolated named session received the reporter's own requests over that session's socket; Herdr attributed the pane to `pi` and persisted `"agent_resume": {"source": "safe-pi", "agent": "pi", "argv": ["safe-pi", "-c"]}` in the session file. After `herdr session stop` and a headless restart, the pane's process tree was `bash /home/sanmoo/.local/bin/safe-pi -c → docker run … --workdir <saved cwd> … safe-pi:current-u1000 pi -e /usr/local/share/safe-pi/herdr-reporter.ts -c`: the pane came back inside a fresh sandbox in its saved working directory, not as a plain shell and never as an unsandboxed Pi. That run persisted the then-shipped `-c`; the shipped command now names the session id, which is what keeps the restart from reopening another session in the same directory. Only the isolated named session was restarted; the live session was never touched. ADR 0004 later changed the reported agent label from `pi` to `safe-pi` with `display_agent: "Pi"` and added the pane release on quit, so the `agent: pi` values quoted here are what that verification observed, not the current label.
- Herdr state attribution for a sandboxed pane comes from the sandbox reporter, not the Herdr-managed integration: the sandbox withholds `HERDR_ENV`/`HERDR_SOCKET_PATH`/`HERDR_PANE_ID` (so the managed integration cannot activate) and hands the reporter the socket and pane under `SAFE_PI_HERDR_*`, so exactly one source owns the pane. The host extensions directory stays mounted read-only at its own path, which keeps the host's relative extension symlinks resolving; only the reporter is loaded from the image with `-e`.
- The sessions directory is visible twice inside the container (under the agent directory and at the container-only report path). Pi uses the latter.
- The sandbox is a filesystem boundary, not a credential boundary: it reads every credential and session in the mounted agent directory.
- Starting a sandbox depends on the network only when the declaration has something to install. Each start first probes the declaration, so an installed toolchain starts silently and works offline; a missing tool that cannot be fetched is a warning, not a block, unless the strict prepare mode is used.
- The toolchain volume holds mise's cache and state as well as its installs. An interrupted install is then recorded and cleaned up on the next start, instead of looking complete, and `latest` pins resolve from the cache without a network round trip.
- An image built before the entrypoint existed is rebuilt on its next use, since running it would start Pi without converging the declared environment.
- Pi updates are explicit (`safe-pi --update`), so the image's Pi can lag the host's; the wrapper warns when the versions differ.
- `pi install` and `pi update` do not work inside the sandbox by design; the host stays the place where Pi packages are managed.
- The sandbox installs an Erlang/OTP built for Ubuntu 22.04 while running on a Debian bookworm image: the entrypoint sets `MISE_ERLANG_PRECOMPILED_OS` to that target and `MISE_ERLANG_COMPILE=false` beside the other mise variables it owns. The foreign build is forward-compatible — ubuntu-22.04's glibc 2.35 is older than bookworm's 2.36, and the image already carries `libssl.so.3` and `libncursesw.so.6` — and `erl` was run inside the image to confirm it. The target is a property of the base image: changing `BASE_IMAGE` to another distribution means revisiting it.
- Two entries of the declaration are pinned while the rest use `latest`. The host, which has no precompiled build on Arch, compiles OTP from source when the pin moves; the sandbox downloads Bob's build. Both sides run the same version from different provenance.
- `erlang.compile = false` is set inside the sandbox only. On the host, where no precompiled build applies, it would turn the next OTP install into a hard failure.
- A pin with no precompiled build for the target fails fast instead of compiling: `--prepare` reports it with a non-zero exit, and a normal start warns and opens Pi with the tools already in the volume.
- The sandbox runs under the host's locale when the image can run UTF-8 under it, and under `C.UTF-8` when it cannot. The image installs `locales`, generates `en_US.UTF-8` (the locale the host forwards) and defaults `LANG` to glibc's built-in `C.UTF-8` for a direct image run; the wrapper forwards `LANG`/`LC_ALL`/`LC_CTYPE` as host identity like the other identity variables; and the entrypoint replaces any of the three the image cannot run UTF-8 under with `C.UTF-8` before convergence, so mise and the command it installs for see it too. That covers a locale the image does not ship, a name carrying no UTF-8 codeset (`C`, `POSIX`), and a name glibc refuses for a modifier the image has no entry for: measured on a host that does have `en_US.utf8`, `LC_ALL=en_US.UTF-8@euro locale charmap` still answers `ANSI_X3.4-1968`. An unavailable locale is therefore an explicit UTF-8 fallback instead of glibc's silent POSIX one, which started the Erlang VM with latin1 native name encoding (`file:native_name_encoding()` returned `latin1` under the forwarded `LANG` and `utf8` under `C.UTF-8`) and made every `elixir` invocation warn, including the one mise runs while installing Elixir. The `locales` package and the generated archive add about 21 MB and 3 MB to the image, and the change rebuilds the image's expensive layers once.
- The sandbox disables the host's `permission-gate` extension instead of keeping its approval prompts: the wrapper already marks the sandbox with `SAFE_PI_SANDBOX=1`, and the extension returns before registering anything when it sees the marker. The container is the boundary; the gate is an advisory host-side guardrail, and inside the sandbox most of what it matches (`sudo`, `mkfs`, `dd`, `fdisk`, `parted`, `/dev/sd*`, `chattr`) has no target at all, while the mounted repository, the sessions directory and the toolchain volume do. A sandbox-only settings overlay and a filtered extensions mount were both rejected on cost: each adds wrapper machinery and one more divergence from the host configuration for the same effect, where the guard leaves the settings and the mounts identical. A sandboxed pane therefore never reports `blocked` to Herdr, because nothing inside the sandbox emits the event the reporter consumes; a pane's `working` and `idle` states are unaffected, and the reporter keeps its `blocked` handling for a source that does emit it. The gate's fail-closed behavior in non-interactive runs goes with it, so an unattended `safe-pi -p` runs a dangerous command rather than refusing it: the boundary, not the gate, is what makes that acceptable.
- The sandbox locale is a property of the image, not of a start: the image ships the one locale the host forwards, and a host that starts forwarding a different one gets `C.UTF-8` rather than a locale it cannot resolve. Adding another shipped locale means regenerating it in the image, which is an image change and therefore a rebuild. An `LC_ALL` the image cannot resolve also makes the entrypoint's own shell report `setlocale: LC_ALL: cannot change locale` once per start, before the entrypoint can replace the value; a mismatched `LANG` alone is silent, and the command the sandbox runs never sees the unresolved value.
